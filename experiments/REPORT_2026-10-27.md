## NAV auto-create (user request 2026-10-27): the iNAV filter bootstraps itself

The one open accuracy gap (external audit F4 — no premium/discount protection
on global ETFs) required NAV files the user had to source manually. Now the
code creates them itself:

- **ensure_nav_csvs()**: instrument_key (NSE_EQ|INF…) -> ISIN; AMFI daily
  NAVAll.txt -> AMFI scheme code + latest NAV; api.mfapi.in/mf/{code} -> up to
  400 days of daily NAV history; writes stock-data/nav/{SYMBOL}.csv.
  Create-if-absent (never clobbers user files); `load-data --fetch-nav`
  forces a refresh. Fully fail-soft offline (nothing written, old note).
- **Wiring**: the daily update path tries once a day when no NAV files exist
  and loads them immediately (filter turns on same-day); `load-data` prints
  coverage; the action panel warns when NAV data is absent OR stale (>4 days).
- **iNAV reference fix**: the filter looked up ONLY the exact-date NAV row,
  which a T-1-published AMFI feed could never satisfy — it now takes the
  latest NAV on/before the date, max NAV_MAX_STALE_DAYS=4 old. Without this
  change the auto-created data would still never fire the filter.
- Selftests 68 -> 74: NAVAll parser, mfapi parser, ISIN extraction, staleness
  window both directions, and an end-to-end create+ingest with stubbed HTTP
  into a temp folder (no network in tests).

## NAV auto-create hardening (live-run follow-up, 2026-10-27, second pass)

Evidence: the first live Windows run of 4db4568 reached GitHub fine but printed
"NAV auto-create could not reach AMFI/mfapi ([WinError 10060])" and the iNAV
filter stayed OFF, so MONQ50 was still bought at a premium with no NAV
protection.

Diagnosis from the log (from the log pattern itself, not live-verified):
1. Single hard-coded AMFI endpoint = single point of failure (timeout/403
   takes the whole feature down for the day).
2. The once-a-day retry lock was stamped BEFORE the attempt, so the first
   failure blocked every retry until the next calendar day.
3. The error path collapsed the real exception into an un-diagnosable
   summary — no way to tell WHICH stage (AMFI download, search, history)
   failed or why.
4. No fallback when the ISIN -> scheme-code map (AMFI) is unreachable.

Fixes (this commit):
- _http_get returns (body, error_detail); every attempt's real reason is
  kept and shown. HTTP is dependency-injected (http_get param) through the
  fetch -> AMFI parse -> mfapi parse -> ensure_nav_csvs chain, so selftests
  hit fixtures only, never the network.
- AMFI NAVAll tried across endpoint fallbacks (www host, portal subdomain,
  NAVOpen fallback) until a parse yields >= MIN_NAVALL_ROWS=1000 rows (the
  dump is 120k+ rows; a stub/HTML page fails loudly instead of silently
  mapping nobody).
- Conservative mfapi name-search fallback when AMFI is unreachable:
  3 query variants, all-or-nothing token containment against the fund's
  journaled name; ambiguous or zero-hit searches are REFUSED — a wrong
  NAV mapping is worse than none.
- Persistent mapping cache stock-data/nav/_nav_map.json records how each
  symbol was resolved (source = amfi-isin | mfapi-search) so refreshes stay
  stable and partial re-runs resume cheaply.
- Retry-lock rewrite: success locks the day (meta nav_autofetch_ok),
  failure only cools off NAV_FAIL_RETRY_HOURS=6 (meta nav_autofetch_fail),
  centralised in _nav_retry_allowed(). A morning failure retries at lunch
  instead of tomorrow; a success never refetches intra-day.
- Console diagnostics: failure notes name each attempted stage with its
  error; action-panel bullets updated (no more stale "once a day" wording).
- Selftests 74 -> 76: AMFI-down + search-fallback resolution fixture, and
  an ambiguous-search-refusal fixture (no wrong mapping ever written).

Still open: the live AMFI/mfapi response formats remain unverifiable from
the sandbox (offline proxy allows github/pypi/npm only). The first real
format test happens on the user's next online run; the new diagnostics will
name the failing stage verbatim if anything still refuses.

strategy constant moved; the backtester is byte-identical in behavior — every fix is on the
live/paper pacing path that the backtest already models correctly (W4-W6 measured the cost
that this round stops paying). The auditor cross-checked AUDIT_LEDGER.md first and proposed
nothing on the do-not-retest list.

* **P0-1 — trickle fired every run.** v10's `_sessions_real` counted downloaded price rows
  up to month-end, but a price table never contains FUTURE dates, so the count was always 0,
  `_sessions_real` always 1, and the =>3-sessions trickle capped every budget at 5,000 for
  the entire month — the autofill pace adopted in audit v4 (ledger row 45) was unreachable.
  Fixed: `sessions_to_calendar()` counts weekdays minus NSE holidays on the calendar.
  (On 2026-10-28 the console printed "only 1 session away" with the real answer being 3.)
* **P0-2 — `day_slices()` bought nothing on a half-empty plan.** 5,000 split across three
  175k gaps = 1,667/name < 2,000 min order -> every share skipped, `applied` stayed 0, loop
  broke, zero orders into a Rs 5.26 L plan that was 52.6% of equity. Fixed: when nothing is
  splittable, the whole budget concentrates on the single largest UNCAPPED gap (one order
  per run; basket completes over a few runs; v5 #3's one-order-per-day and the dust floor
  both intact). Together, P0-1+P0-2 had restored the flat-5000/day (~1pp CAGR per 10
  sessions, W4-W6) regime while ALSO capping it at zero — the largest profitability bug in
  the current codebase, now dead.
* **P0-3 / P2-3 — false diagnostics.** "Every remaining gap is below the minimum trade
  value" and "budget was spent earlier today / ETFs are full" both named causes that were
  measurably false in the run (gaps ~1.75L; first run of the day). Messages now name the
  surviving causes (budget already used / sub-min gaps / liquidity caps spent).
* **P1-1 — survivorship note never fired on a fresh install** (scan runs before the day's
  price download, so the oldest-price condition was vacuous). Journal-side branch added:
  every ETF first_seen == today = fresh-install signature; same weekly-cadenced note.
* **P1-3 — config note only (Option B):** INVEST_PER_DAY 5000 < 2000 x 5 means the floor
  budget places ONE order per run by design; documented, value unchanged. The auditor's
  Option A (raise the floor) was NOT taken: changing two things in one commit would hide
  which fix moved the behaviour — per the auditor's own order-of-work instruction.
* **P2-1/P2-2 — labels:** "PORTFOLIO AFTER THIS CYCLE" retitled "AFTER MONTHLY REBALANCE
  (before today's buying)" (deploy runs later); "session(s)" pluralised properly.
* **P1-2 — recorded as DEFERRED ledger #114:** compound risk_scale (DD tier x bear regime
  = 0.25 combined) is materially calibrated: W16/R13G measured each axis alone, never the
  joint case. No code change without a backtest.
