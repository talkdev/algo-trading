# NIFTY Intraday Options Algo-Trading Engine — Codebase Guide

> **Audience:** an AI assistant (or engineer) picking up this repo cold and expected to ship code changes fast. Read §1 before touching anything — the repo is **mid-migration between two engine generations**, and knowing which generation a file belongs to is the difference between a 30-second fix and an hour of confused debugging.

---

## 1. READ THIS FIRST — two generations of the engine, and exactly where the seam is

The repo contains **13 Python files** forming (nominally) one engine, but they split cleanly into an **old generation** and a **new generation**, plus two files that are **caught in between** and currently broken. This is not guesswork — it's stated in the files' own docstrings and confirmed by tracing every import.

### Old generation ("5-file architecture", `FILE 1 of 5` … `FILE 5 of 5` headers)

`nifty_algo_core.py` (File 1) → `market_data_engine.py` (File 2) → `strategy_engine.py` (File 3) → `execution_engine.py` (File 4) → `main.py` (File 5).

This chain **is fully self-consistent and is what `python main.py` actually runs today.** `strategy_engine.py` and `execution_engine.py` still `from nifty_algo_core import (...)` / `from market_data_engine import MarketDataEngine, ensure_column`, and every signal key they read (`volatility_condition`, `trend_condition`, `direction`, `adx`, `vwap_signal`, `pcr_signal`, `skew_signal`, `preferred_sell_side`, `spot_vs_or`, `active_expiry`, …) and every `Config` field they read (`config.stt_rate`, `config.brokerage_per_order`, `config.exchange_txn_rate`, …) match `nifty_algo_core.py`/`market_data_engine.py` exactly. **This chain imports and runs.**

### New generation ("v3.0 / v4.1", no `FILE n of 5` header)

`core.py` explicitly says *"Evolved from nifty_algo_core.py"* and `data_engine.py` says *"Evolved from market_data_engine.py."* They are a rewrite with a materially different design: regime-based classification (`vol_regime`/`price_regime`/`positioning_regime`/`final_regime` instead of `volatility_condition`/`trend_condition`/`direction`), DTE-aware VRP anomaly bounds, an EV-gate sizing model, and a much larger `Config`. `calibration_engine.py` (`from core import (...)`) is a new, separate, Bayesian-shrinkage calibrator built for this generation. These three files (`core.py`, `data_engine.py`, `calibration_engine.py`) are mutually self-consistent and importable.

### The two files caught in the middle (currently broken)

- **`regime_engine.py`** does `from nifty_algo_core import (..., ExpiryCalendar, get_high_impact_events, ...)` and `from market_data_engine import MarketDataEngine, TechnicalEngine`. **`ExpiryCalendar`, `get_high_impact_events`, and `TechnicalEngine` do not exist in the old-generation files — they only exist in `core.py`/`data_engine.py`.** So `regime_engine.py` fails at import time (`ImportError`) against the files it actually names. It was written against the new generation but never had its two import lines updated. **This is a one-line-category fix**: change its two import statements to `from core import (...)` / `from data_engine import MarketDataEngine, TechnicalEngine`, then re-check every symbol it references is actually present in those files (a couple aren't — see §7).
- **`backtest_engine.py`** (`import core, data_engine, regime_engine, strategy_engine, execution_engine, calibration_engine`) constructs `strategy_engine.StrategyEngine(config, db, me, ce, logger)` (5 args, includes a `CalibrationEngine`) and `execution_engine.ExecutionEngine(config, db, me, ce, client, logger)` (6 args, includes `ce`). **The actual `strategy_engine.py`/`execution_engine.py` in the repo take 4 and 5 args respectively, with no `ce` parameter, and are old-generation.** So `backtest_engine.py` cannot run (`TypeError` on construction, on top of the `regime_engine.py` `ImportError` it also transitively hits). It is written against an **aspirational future state**: `strategy_engine.py` and `execution_engine.py` rewritten to the new generation's API. Read it anyway — its header comment and `STAGE_ORDER` are the best design document in the repo for where this is headed and what the real strategy gate order is.

### `verify_all.py` is the project's own admission of this state

It shells out to run each file's `_self_test()`/`--test`: `data_engine.py`, `regime_engine.py`, `execution_engine.py`, `strategy_engine.py`, `calibration_engine.py`, `backtest_engine.py --test`, `eod_report.py --test`. Tracing imports tells you the result before you even run it:

- **PASS today**: `data_engine.py`, `calibration_engine.py` (both new-generation, self-consistent, self-tests degrade gracefully without a live token), `strategy_engine.py`, `execution_engine.py` (both old-generation, self-consistent, same graceful degradation).
- **FAIL today**: `regime_engine.py` (ImportError, see above), `backtest_engine.py --test` (ImportError via `regime_engine`, then would also hit the `StrategyEngine`/`ExecutionEngine` constructor mismatch once that's fixed). `eod_report.py` doesn't even parse a `--test` flag (only `--date`) — it'll either silently ignore it and try the hardcoded `TARGET_DATE`, or fail if no DB exists at the default path.

### What this means for any task you're given

1. **"Run the engine" / "trade paper"** → `python main.py` works today, using the **old generation** (`nifty_algo_core.py`/`market_data_engine.py`/`strategy_engine.py`/`execution_engine.py`). It does **not** use `core.py`, `data_engine.py`, `regime_engine.py`, or `calibration_engine.py` at all — none of those are imported anywhere in the old chain. If you're asked to change "the strategy logic" or "the regime classification" without qualification, ask (or infer from context) whether they mean the live engine (old generation, `strategy_engine.py`'s `_select_strategy`) or the newer regime-based design (`regime_engine.py`, not currently wired to anything runnable).
2. **"Fix a bug in `strategy_engine.py`/`execution_engine.py`"** → these are live, running code. Edit them in place using the old-generation vocabulary; don't "helpfully" rename things to match `core.py`/`data_engine.py` unless the task is explicitly the migration itself.
3. **"Run the backtester"** → `backtest_engine.py --audit` and `--test` will not currently succeed end-to-end (see above). If asked to get it working, the real task is **the migration**: port `strategy_engine.py`/`execution_engine.py` to import from `core`/`data_engine`, accept a `CalibrationEngine` instance, and speak the new signal vocabulary — using the *old* `strategy_engine.py`/`execution_engine.py` as the source of the actual trading logic to preserve, and `regime_engine.py` + `backtest_engine.py`'s expectations as the target API to land on.
4. **"Fix `regime_engine.py`"** → swap its two import lines to the new generation (`core`/`data_engine`) and reconcile the small number of symbol mismatches (§7). It is not, and cannot become, old-generation-compatible (`ExpiryCalendar`/`TechnicalEngine` don't exist there).
5. **`eod_report.py` and `split_db_per_day.py`** are safe, independent utilities — see §3. `eod_report.py` in particular is schema-tolerant and will produce a report from a DB written by *either* generation (it does `SELECT *` and checks column/table existence defensively), which makes it a good reference for "what fields exist across both schemas."

## 2. Domain in one paragraph

This is a systematic options-selling (and occasionally options-buying) algo for **NIFTY 50 index weekly options** on the Indian NSE, trading through the **Upstox** broker API. It runs a 5-minute decision loop during market hours (09:15/10:00–15:00/15:30 IST, generation-dependent), classifies the day's volatility/trend/positioning condition, decides whether to sell premium (iron condor, iron butterfly, credit spreads) or buy it (debit spreads, straddles) or stand aside, sizes the trade against a risk-per-trade/risk-per-day budget, executes (paper or live), and manages exits via a priority ladder (premium stop, price stop, profit target, profit-lock trailing stop, VWAP breach, ADX breach, delta breach, hard time exit). Everything is logged to SQLite for a nightly forensic report and (new generation only) for self-calibration of thresholds from historical performance.

Core edge thesis, unchanged across both generations: **sell premium when implied vol (from the option chain) is rich relative to realized vol (Parkinson estimator on intraday bars)**. That gap is **VRP** (variance/volatility risk premium), in percentage points (pp).

## 4. Database: two separate SQLite files, two schemas

- **`data/nifty_algo.db`** (old generation, `nifty_algo_core.py::SCHEMA_SQL`) — written by `main.py`/`market_data_engine.py`/`strategy_engine.py`/`execution_engine.py` today. Tables: `session_state`, `positions`, `position_legs`, `option_chain_snapshot`, `cycle_log`, `trade_entries`, `trade_exits`, `daily_summary`, `audit_log`, `api_call_log`, `instrument_master`. No `regime_decisions`, no `calibration_state`, no `phantom_trades`.
- **`data/nifty_algo_v3.db`** (new generation, `core.py::SCHEMA_SQL`) — written only when `data_engine.py`/`calibration_engine.py`/(fixed) `regime_engine.py` are actually run (currently: only via each file's own self-test, or once the migration lands). Superset of the old schema plus `regime_decisions`, `calibration_state`, `phantom_trades`, `exit_quality_log`, `regime_accuracy_scores`, `expiry_results`, `vix_history`, `market_snapshots`, `options_chain` (condensed ATM chain), richer `positions`/`trade_entries` (regime/confidence/event columns, `entry_vrp_smoothed`, `opening_straddle_at_entry`, `is_borderline_sell`, …). Migrations are additive `ALTER TABLE` statements in `MIGRATION_SQL`, applied idempotently — **when adding a column here, add it to both `SCHEMA_SQL` and `MIGRATION_SQL`**, or existing DBs won't pick it up.

`backtest_engine.py` and `split_db_per_day.py` both target the new-generation `nifty_algo_v3.db`. `eod_report.py` will happily open either (path comes from whichever `env.txt`'s `DB_PATH` points at).

Key tables to know regardless of generation:

- **`session_state`** — one row per trading day, the day's mutable state (opening range, VIX regime, entry window, size multiplier, capital, daily P&L, halt flags, consecutive-stops). This is the in-memory `self.state` dict on `MarketDataEngine`, saved back after every mutation — restart-safe by design in both generations.
- **`positions`**/**`position_legs`** — one row per position/leg, mutated in place as the position moves through its lifecycle.
- **`trade_entries`**/**`trade_exits`** — append-only richer history, used for reporting/calibration queries (joins on `position_id`).
- **`cycle_log`** — one row every ~5-minute cycle: the full signal snapshot + action taken + no-trade reason. **Primary place to debug "why didn't it trade" / "why did it exit."**
- **`option_chain_snapshot`** — full chain every cycle. This is what `backtest_engine.py` replays; without enough days of it (from real paper/live runs) there's nothing to backtest (`--audit` tells you what's usable).
- **`daily_summary`** — one row per day, EOD aggregate.
- **`strategy_decisions`** — every `decide()` call, ENTER or NO_TRADE with full reason + params/signals JSON.

## 5. Config systems (two, not compatible)

**Old (`nifty_algo_core.py::Config`/`load_config()`):** every tunable lives in `env.txt` (`ENV_TEMPLATE` shows the full expected set: credentials, `PAPER_TRADE_MODE`, `STARTING_CAPITAL`, `MAX_DAILY_LOSS_PCT`, `MAX_RISK_PER_TRADE_PCT`, `NIFTY_LOT_SIZE`/`NIFTY_STRIKE_STEP`, `STT_RATE`/`BROKERAGE_PER_ORDER`/`EXCHANGE_TXN_RATE`, trading window, position limits, infra). Trading window default is **10:00–15:00** (explicit stated requirement in the docstring). `MAX_RISK_PER_TRADE_PCT` is clamped `< MAX_DAILY_LOSS_PCT/3`. High-impact events load from `high_impact_events.json` (start empty, user-populated).

**New (`core.py::Config`/`load_config()`):** as of "v4.1," `env.txt` holds **only `UPSTOX_ACCESS_TOKEN=`** — every other tunable (~120 fields) has a hardcoded default in `load_config()` reproducing the previously-shipped `env.txt` values; any key still present in `env.txt`/OS env overrides its default. Trading window default is **09:45–14:00** (hard exit 15:00, Tuesday-specific 12:30 last-entry/15:00 hard-exit). `paper_trade_mode` defaults `True` and is force-reset to `True` unless `LIVE_RATES_VERIFIED=true` is also set. Same `max_risk_per_trade_pct < max_daily_loss_pct/3` clamp, different defaults (1.2%/4.0% vs. old 0.6%/2.0%). A large block of fields (`v3.1`/`v3.2`/`v3.3` prefixed in comments — `stop_mult_dte0`, `target_pct_dte0`, `price_stop_wing_frac`, `credit_risk_ratio_dte0_early/mid/late`, `iv_sigma_cap_ratio`, `ev_blend_*_w`, `min_lots_fraction`, `day_move_range_factor`, …) each carry a long comment documenting a **specific dated production incident** (repeatedly referencing a `2026-09-08` VIX-11 0DTE session) that motivated the exact value. **Read the comment above a new-generation constant before changing it** — it is regression-test documentation, not arbitrary tuning.

Both configs independently guard against accidental live trading: `UpstoxClient.place_order()`/`cancel_order()` refuse under `paper_trade_mode=True` (defense in depth beneath whatever the execution engine decides), and `LiveOrderExecutor` in `execution_engine.py` refuses to even construct under paper mode.

Lot size defaults to **65** in both generations — verify against the live NSE contract spec before trading live; the code prints a manual reminder but does not auto-verify against a broker instrument-master endpoint (explicitly noted as unverified in both `nifty_algo_core.py`'s header and `main.py`'s `_verify_lot_size()`).

## 6. Core domain vocabulary

- **DTE** — trading-day count to next weekly (Tuesday) expiry. DTE 0 = expiry day. Old generation computes this ad hoc per-file; new generation centralizes it in `core.ExpiryCalendar` (also handles holiday roll-back, monthly-expiry detection, day-type labels `EXPIRY_DAY`/`PRE_EXPIRY`/`NEW_CYCLE`/`WEEKEND_RISK`/`MID_WEEK`).
- **VRP (variance/volatility risk premium)** — `ATM IV% − Parkinson RV%`, in percentage points. Positive = options rich vs. realized movement = sell-premium edge. Old generation: fixed bands (`VERY_RICH>8`, `RICH>4`, `FAIR>2`, `THIN>0.5`, `CHEAP`, `INVERTED`), Parkinson RV over the last 3 complete sessions, cached once/day. New generation: exponentially-weighted smoothing buffer, DTE-aware anomaly bound (looser on 0DTE because a low realized/implied ratio is *normal* near expiry — `core.vrp_anomaly_limit()`), intraday recency-weighted Parkinson estimator, calibrated (not fixed) sell/fair thresholds.
- **OR (opening range)** — old generation: 09:15–09:29, fixed-point bands (`VERY_NARROW<40pts` … `VERY_WIDE≥150pts`). New generation: 09:15–09:45, classified by the *more conservative* of width-as-%-of-spot and width-vs-opening-straddle (scale-invariant as NIFTY's index level rises).
- **Trend condition** — old generation: a hand-built lookup table keyed by (OR condition, ADX condition) → label+score (`TREND_LOOKUP`). New generation: `regime_engine.py`'s multi-factor `PriceRegime`/majority-vote system (not currently reachable — see §1).
- **Exit priority ladder** (`execution_engine.py::monitor_position`, both generations conceptually — old-generation is what's live): premium stop (with time-based tightening + profit-lock trailing) → price-based spot-move stop → profit target → VWAP breach (full close for directional spreads, one-side close for condor/butterfly) → ADX trend breach → portfolio delta breach → hard exit time → short-leg delta breach.
- **Paper vs. live** — `PaperOrderExecutor` fills at bid(sell)/ask(buy) from the live chain; `LiveOrderExecutor` places real Upstox orders and refuses to construct under `paper_trade_mode=True`. Multiple independent guards (§5) prevent accidental live trading.
- **Regimes** (new generation only, `regime_engine.py`): `VolatilityRegime` (STRONG_SELL_PREMIUM/SELL_PREMIUM/NEUTRAL/BUY_OPTIONS/HIGH_VOL_CAUTION/ABORT), `PriceRegime`, `PositioningRegime` (from OI walls/PCR/skew), combined by majority vote into `FinalRegime` with a `ConfidenceLevel` (HIGH/MEDIUM/LOW/NONE from 3/2/1/0 signal agreements) and a day-of-week × confidence × event × VIX-level `size_multiplier`.

## 7. Concrete punch list if asked to "finish the migration" / "make everything green in `verify_all.py`"

1. **`regime_engine.py` imports.** Change:
   ```python
   from nifty_algo_core import (Config, Database, RateLimiter, UpstoxClient,
       ExpiryCalendar, now_ist, today_ist, load_config, setup_logging,
       get_nse_holidays, get_high_impact_events,
       INSTRUMENT_KEY_NIFTY_SPOT, INSTRUMENT_KEY_INDIA_VIX)
   from market_data_engine import MarketDataEngine, TechnicalEngine
   ```

   to `from core import (...)` / `from data_engine import MarketDataEngine, TechnicalEngine`. Then check every other symbol it uses against `core.py`'s actual exports (e.g. it references `self.config.vix_extreme_high`, `ivr_sell`/`ivr_buy`/`ivr_neutral_low`, `iv_hv_sell`/`iv_hv_neutral`/`iv_hv_buy`, `straddle_ratio_sell`/`straddle_ratio_neutral_h/l`, `pcr_extreme_bull`/`pcr_extreme_bear`, `vix_roc_emergency_pct`, `vix_roc_lookback_min`, `regime_confirm_cycles` — **confirm each exists in `core.py::Config`'s current field list**; several of these look like they may be missing/renamed relative to what's shown in §5, since `core.py`'s field list doesn't obviously include them all. This is exactly the kind of mismatch to grep for before assuming the import fix alone is sufficient.)
2. **`strategy_engine.py`/`execution_engine.py` migration.** Port both from `nifty_algo_core`/`market_data_engine` imports and the old signal vocabulary to `core`/`data_engine` + the `vol_regime`/`price_regime`/`positioning_regime`/`final_regime`/`vrp_smoothed` vocabulary, and add a `CalibrationEngine` (`calibration_engine.CalibrationEngine`) constructor parameter to match what `backtest_engine.py` already expects (`StrategyEngine(config, db, me, ce, logger)`, `ExecutionEngine(config, db, me, ce, client, logger)`). The actual trading *logic* (gate order, strategy-selection matrix, cost model, exit ladder) should carry over from the current old-generation files — the task is translating the field names and threshold sources (static dict → `CalibrationState`/`config` new-generation fields), not re-deriving the strategy.
3. **`main.py` rewrite** to wire `core`+`data_engine`+`regime_engine`+`calibration_engine`+ the migrated `strategy_engine`/`execution_engine` together, mirroring how `backtest_engine.py::BacktestRunner._build()` constructs them for replay.
4. **Validate** with `python backtest_engine.py --test` (synthetic self-test of the whole plumbing — clock injection, replay client, decision path, exit ladder, fills, cost accounting; says nothing about strategy profitability, only that the wiring works) and then `python verify_all.py`.
5. Decide what happens to `nifty_algo_core.py`/`market_data_engine.py` once nothing imports them anymore (archive vs. delete) — until that decision is made, don't delete them, since they're what `main.py` actually runs.

## 8. Where to look for a given task (assuming the old/live generation unless stated otherwise)

- **"Why didn't the live engine take a trade on date X"** → `data/nifty_algo.db`: `cycle_log.no_trade_reason` / `strategy_decisions` table for that date, or `eod_report.py --date X` (works against either DB).
- **"Change a live threshold"** → `env.txt` (old generation reads every tunable from there) or the default in `nifty_algo_core.py::load_config()`; hardcoded strategy constants (`DTE_REQUIREMENTS`, `MIN_CREDITS`, `PRICE_STOPS`, `TARGET_PCT_BY_DAY`, `LOT_CAPS_BY_DAY`) live at the top of `strategy_engine.py`.
- **"Add a new strategy type" (live engine)** → `strategy_engine.py`: extend `DTE_REQUIREMENTS`/`MIN_CREDITS`/`PRICE_STOPS`, `_select_strategy`, `_validate_strategy_entry_rules`, `_build_legs_spec`, and the cost/sizing math in `compute_strategy_params`. Mirror any new exit behavior in `execution_engine.py::monitor_position`.
- **"Add a new market signal / indicator" (live engine)** → `market_data_engine.py`, wire it into `run_cycle()`'s `signals` dict, persist in `_persist_cycle_log`, add the column to `nifty_algo_core.py::SCHEMA_SQL`.
- **"Work on the new regime-based design"** → `core.py`/`data_engine.py`/`regime_engine.py`/`calibration_engine.py`, but first fix `regime_engine.py`'s imports (§7) if you need it to actually run.
- **"Fix/extend the nightly report"** → `eod_report.py` — independent of both engines' Python APIs (reads DB directly), low-risk to edit. Add a `compute_*` function, wire into `generate_report()`'s `md.append(...)` sequence and the `raw_exports` dict.
- **"Understand the intended final gate order / architecture"** → `backtest_engine.py`'s header comment and `STAGE_ORDER` list — written with unusual care and is more trustworthy than inferring gate order from reading `strategy_engine.py` top-to-bottom.
- **"Shrink/share the new-generation DB"** → `split_db_per_day.py`.
- **"Smoke-test after any change"** → `python verify_all.py` (know going in which entries currently fail and why — §1 — so you can tell a regression from a pre-existing failure).

## 9. Conventions to preserve

- All timestamps are IST (`now_ist()`/`today_ist()`, via `zoneinfo`/`pytz` fallback in both generations). Never use naive UTC `datetime.now()`.
- Money in Rupees (`Rs`), option premium in index points (`pts`), lot size default 65 shares.
- Every DB write goes through `Database.insert`/`.update`/`.upsert`/`.ensure_column` — don't hand-roll SQL against the connection directly except in read-only reporting/utility scripts (`eod_report.py`, `split_db_per_day.py`, `backtest_engine.py`'s `HistoricalStore` are the sanctioned exceptions, and they open read-only where possible).
- Functions touching external state (API calls, DB) are defensive: broad `try/except`, log-and-continue rather than crash the 5-minute loop. Preserve this — a single bad cycle should never kill the day's session.
- New-generation inline comments prefixed `v3.1`/`v3.2`/`v3.3`/etc. document *why* a number is what it is, tied to a specific dated incident. Treat as regression-test documentation; don't delete when refactoring nearby code.
- `paper_trade_mode` defense-in-depth (independent guards at the `Config`, `UpstoxClient`, and `LiveOrderExecutor` layers) is intentional redundancy, not accidental duplication — preserve all layers when touching live-order-routing code.
